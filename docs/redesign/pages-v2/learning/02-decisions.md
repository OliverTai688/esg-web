## 一、跨區塊的先行判斷

看完 24 個選項後，有四件事必須先在整頁層級決定：

1. **「選主題」只能出現一次。** S2-A（花瓣分頁）、S3-C（類型分頁）、S4-B（主題分頁）、S4-C（主題分組）都是「先選再看」。同一頁連續兩段做同一件事，後一段就沒有存在的理由。決定：主題的選擇只在 S2（花）；S4 的篩選籤預設是「全部」，是清單的工具而不是入口。
2. **大花瓣只能出現一次。** S1-C、S3-A、文章頁文末都用「一片大花瓣托一篇文章」。`/learning` 上只留在 S3；文章頁文末是另一頁，可以再用一次（它就是「下一片」）。
3. **花瓣門＋方塊門不在知識區用。** S5-C、文章頁 C 的兩道門很清楚，但那是 `/consulting`（合龍點）的主角形狀。知識區的收尾一律用共用的 `CtaBand`，分流寫在一句話裡。
4. **兩頁必須長得不一樣。** insights-C（清單＋顯示更多）與 S4-A 幾乎相同。`/learning` 用「圓＋主題」，`/insights` 用「線＋日期」，凡是會讓兩頁變像的選項都扣主線分。

## 四、每個區塊選用的 UX 元件

| 區塊 | 內容型態 | 元件 | 為什麼是它 |
|---|---|---|---|
| `/learning` S1 | 一句話＋兩個數字 | 形狀本身（兩片花瓣承載數字） | 能用形狀說就不用字 |
| `/learning` S2 | 同一層級、互斥的六組內容 | **分頁（花瓣當籤）**：`TopicExplorer`，`role="tablist"`，面板全在 HTML、未選的 `hidden`，←／→ 切換 | 六組內容結構相同、一次只需要看一組；共用 `Tabs` 的籤列是一排膠囊，放不成一朵花，所以在 `src/components/learning/` 做了花瓣版，語意與鍵盤行為相同 |
| `/learning` S3 | 一篇主打 | 不需要互動元件：一張葉形卡＋一顆主按鈕 | 只有一個決定，任何互動都是多的 |
| `/learning` S4 | 很多筆要篩選的內容 | **篩選籤＋「顯示全部」**（手機先 4 列、桌機先 6 列）：`PostFilter` | `00` 第六節對這個型態的指定；16 篇還不需要分頁或搜尋 |
| `/learning` S5、其他頁收尾 | 一個行動＋一個備案 | 共用 `CtaBand` | 全站收尾一致 |
| `/insights` N2 | 一則頭條＋四筆近期 | 大日期頭條＋日期列（純連結） | 最新的幾篇不該被摺起來 |
| `/insights` N3 | 多筆「標題（月份）＋內容（該月文章）」 | **`FoldList`**（原生 `<details>`，同名互斥） | 月份會一直增加，可展開列的高度不隨文章數成長；沒有 JS 也能用、頁內搜尋會展開 |
| `/insights` N4 | 六個去處 | 形狀本身（六片花瓣就是連結） | 回主題的動作和 `/learning` 的花是同一個形狀 |
| 文章頁文首 | 這篇是誰寫的、屬於哪個主題 | 小花徽＋主題連結＋一行資訊 | 不需要互動 |
| 文章頁目錄 | 長文的段落 | 共用 **`ChapterNav`**（小標 ≥ 3 段才出現，固定在導覽列下方、標出目前段落） | 和其他分頁的章節膠囊是同一個元件、同一種行為；文章的「章節」就是它的小標 |
| 文章頁文末 | 一篇建議 | 一張葉形卡（同主題下一篇） | 一個建議比三張卡清楚 |
| 主題列表頁 | 2–5 筆同型內容 | 編號列（純連結） | 這一頁的工作是「一次看完這個主題有幾篇」，滑軌與展開都會讓它變慢 |

沒有用到的元件與原因：`SnapRail`——知識區沒有「4 張以上同型卡片而且值得一張一張看」的內容，清單用列更快；`Sheet`——文章標題與說明都需要被搜尋引擎讀到；`ReadMore`——沒有長段客戶原文（長文就是文章本身）。

## 六、對 `01-page-plan.md` 的修正

1. **閱讀進度條不另外做。** 實作後才發現全站導覽列下緣本來就有一條捲動進度線（`Navbar.tsx`）；再加一條「文章進度」會變成兩條長度不同的線疊在一起。已移除自己的進度條。現在文章頁的進度＝導覽列那條線（量的是整頁，不是內文）＋段落籤標出目前段落。要讓那條線在文章頁只量內文，需要改共用檔，列在回報的「共用檔修改需求」。
2. **目錄從文首的一排籤改成固定的段落籤。** 提案 A 的目錄在文首、不跟著捲動（列為風險）。改用共用的 `ChapterNav`：小標三段以上才出現，固定在導覽列下方、標出目前段落，文章結束就跟著捲走。順便解決了 B 的優點（目錄永遠在旁邊），又不需要側欄。
3. **文章摘要改當導言。** 計畫寫「文首 ≤ 110 字」時摘要還在文首。實作時把摘要放到內文第一段（放大、加粗），文首只剩返回、主題、標題、一行資訊。
4. **「顯示更多（還有 N 篇）」改成「顯示全部 N 篇」。** 手機先顯示 4 列、桌機 6 列，「還有幾篇」在兩種寬度下數字不同，同一份 HTML 寫不出來；改報總數就沒有這個問題。
5. **篩選籤的順序跟著花。** 六個主題依花瓣順序排，不在花上的分類（ESG共學坊公告）排最後。
6. **`/learning` 的返回連結多一種落點。** 公告類文章沒有對應的花瓣，返回連結改到 `#articles`（原本是頁面頂端），符合「回到它所屬的區塊」。
7. **英文花瓣用短名。** 斜的四片花瓣在手機上最寬只有約 70px，辭典的 `sections.*.short` 提供花瓣上的名稱（英文：Innovation／Market Edge／ESG & CSR／Partnership／Communication／Interviews；中文與全名相同）。面板標題、篩選籤、文章頁仍用全名。
